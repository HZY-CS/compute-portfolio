## 一、实验环境
- **平台**：AutoDL 云服务器
- **GPU**：NVIDIA GeForce RTX 3090 / RTX 4090
- **CUDA 版本**：11.8
- **编译命令**：`nvcc -o GEMM GEMM.cu`
- **基准测试**：矩阵规模 \(M=N=K=2048\)（后续拉大至 8192 测试内存墙）

## 二、实验数据记录

### 1. 基础版本对比（基于 `SGEMM-V1.cu`，TILE_SIZE = 16）
- **矩阵规模**：\(2048 \times 2048 \times 2048\)
- **正确性验证**：`Verification errors: 0 / 4194304`（与 CPU 算出的参考值完全一致）

| 版本 | 核心策略 | 耗时 (ms) | 加速比 |
| :--- | :--- | :--- | :--- |

### 2. 进阶大规模与架构极限测试（基于 `SGEMM-V2-tiled_32.cu` 及后续实测）
- **矩阵规模**：\(8192 \times 8192 \times 8192\)
- **现象记录**：
  - 当 `TILE_SIZE = 32` 时，Tiled 耗时与 Naive 基本持平（甚至微弱落后至 0.96x）。
  - 当尝试 `TILE_SIZE = 64` 时，程序瞬间返回 0.001ms，并跑出 2000 亿 GFLOPS 的荒谬数据。

## 三、深度现象分析与硬核排坑

### 1. 为什么 Tiled 版本的加速比不如预期（只有 1.30x）？
- **L1/L2 缓存的魔法**：在 2048 甚至 8192 规模下，Naive 版的相邻线程访问连续的内存地址（合并访问），且大量重复读取。RTX 30/40 系的 L1/L2 缓存极大，硬件自动进行了“广播”和命中缓存。Naive 版实际并没有被 HBM 显存带宽卡死。
- **同步开销（Sync）吃掉了收益**：Tiled 版为了保证数据复用，引入了大量 `__syncthreads()`。当 \(K=8192\) 时，若 `TILE_SIZE=16` 则需同步 512 次，若 `TILE_SIZE=32` 则需同步 256 次。大 Block 的单次对齐代价极高。

### 2. 为什么 TILE_SIZE = 64 会瞬间跑完并报错？
- **物理死线**：NVIDIA GPU 规定，单个 Block 的最大线程数为 **1024**。
- `64 x 64 = 4096` 个线程远超硬件上限，导致 Kernel 启动失败。而由于代码中没有使用 `cudaGetLastError()` 检查启动状态，计时器捕获了瞬间失败的 0ms，导致计算出的 GFLOPS 虚高（2000 亿+）。

### 3. 跷跷板理论（Occupancy vs Synchronization）
- 增大 Block Size 会减少 Grid 中的 Block 总数（减少同步次数）。
- 但是，过大的 Block（如 1024 线程）会占满 SM 的所有资源，导致 Occupancy（占用率）降低。如果 GPU 没有足够的其他 Block 来切换，就无法隐藏内存延迟。

## 四、下一步优化计划
单纯的 Shared Memory 分块在当前硬件上已触及瓶颈。下一步将引入：
1. **Thread Tiling（寄存器分块）**：让每个线程计算多个 C 元素，降低 Shared Memory 访问频率。
2. **Double Buffering（双缓冲）**：利用异步拷贝，让“搬运数据”和“计算数据”重叠进行。
3. **代码健壮性**：在每次 `<<< >>>` 启动后加入 `CHECK(cudaGetLastError());`。
