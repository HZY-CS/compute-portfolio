# SGEMM 单精度矩阵乘法深度优化与架构剖析（总报告）

本模块记录了针对单精度矩阵乘法（SGEMM）从无到有、从基础共享内存到工业级寄存器分块的完整优化演进过程。实验基于真实硬件进行了多次迭代与对比。

## 一、实验环境
- **硬件平台**：AutoDL 云服务器 (NVIDIA GeForce RTX 4080 SUPER)
- **软件环境**：CUDA 11.8, GCC 11
- **测试规模**：\(M=N=K=8192\) （单精度 Float32）
- **评估方式**：预热后运行 10 次取平均时间，通过 CPU 交叉验证结果正确性。

## 三、深度技术剖析与排坑记录

### 1. 为什么单纯的 Shared Memory Tiling 会失效？
在早期的 V1/V2 测试中，发现 Tiled 版本相比 Naive 提升极小，甚至因为同步开销而变慢。深度分析原因如下：
- **L1/L2 缓存的护城河**：RTX 40 系显卡具有极大的 L2 缓存。Naive 版本虽然是重复读取，但相邻线程访问连续地址，硬件的高效合并与缓存广播机制直接兜底了访存压力。
- **同步开销（跷跷板效应）**：`__syncthreads()` 在大 Block 下代价极高。1024 个线程的“齐步走”导致了严重的等待，反而拖垮了性能。

### 2. 为什么 V3 寄存器分块能实现 2.12x 突破？
V3 版本引入了工业级优化的核心思想：**Thread Tiling（寄存器分块）**。
- **单线程计算多个元素**：每个线程利用 `sum00, sum01, sum10, sum11` 同时计算 2x2=4 个 C 元素。
- **算术强度飙升**：在 K 维度的循环中，从 Shared Memory 读取一次 `a0, a1, b0, b1`，直接完成 4 次乘加运算。**数据复用率提升 4 倍，Shared Memory 的访问频率大幅降低。**
- **实测结果**：GFLOPS 突破 5900，加速比稳定在 2.12x，真正压榨出了显卡的算力。

### 3. 消除 Bank Conflict（Padding 魔法）
在声明共享内存时，摒弃了传统的 `As[32][32]`，采用了 `As[32][33]`（即 `+1` Padding）。这直接打破了 32 个 Bank 的对称映射，彻底消除了多线程访问同列数据时产生的 Bank Conflict 串行等待。

### 4. 硬件物理死线踩坑（TILE_SIZE=64 崩溃事件）
在测试中，曾尝试将 `TILE_SIZE` 设为 64。程序瞬间返回并跑出荒谬的 2000 亿 GFLOPS。原因在于 `64 * 64 = 4096` 个线程，直接突破了 NVIDIA GPU 单 Block 最大 **1024 线程**的硬件限制，导致 Kernel 根本无法启动。这也反向证明了加入 `cudaGetLastError()` 检查的重要性。

## 四、下一步优化展望（DeepGEMM 进阶方向）
当前 V3 版本仍是单缓冲（Synchronous）模型。未来对标工业界（如 DeepGEMM）的优化路径：
1. **Double Buffering（双缓冲流水线）**：利用 `cp.async` 或 TMA 技术，在计算当前 Tile 的同时，异步加载下一个 Tile，实现“搬运与计算重叠”。
2. **Thread Tiling 扩展**：从 2x2 扩展至 4x4 甚至 8x8，进一步将寄存器压榨到极限。
3. **向量化访存 (Vectorized Load)**：使用 `float4` 进行 128-bit 宽度的读取，将带宽利用率拉满。
